## 2. Backend Architecture — N-Layer Separation

### Dependency Direction (Strictly flows inward)

```
TeacherPlatform (API)  ->  Service  ->  Repository  ->  DAL  ->  BusinessObject
```

- Each layer only references projects directly below it.
- **NEVER** reference `TeacherPlatform` from `Service`, `Repository`, `DAL`, or `BusinessObject`.
- **NEVER** skip layers (e.g., Controllers calling DAOs directly).

### Layer-by-Layer Rules

#### Layer 1 — `BusinessObject/`
- **Contains**: EF Core entity models, domain enums, and DTOs.
- **Naming**: `PascalCase.cs` matching the domain entity (`Classroom.cs`, `Submission.cs`, `Student.cs`).
- **DTOs**: Group in `BusinessObject/Dtos/{Feature}/` (e.g., `Dtos/Class/ClassCreateDto.cs`).
- **Rule**: Pure data shapes only. Absolutely no database queries, business logic, or HTTP references.

#### Layer 2 — `DAL/` (Data Access Layer)
- **Contains**: `DbContext` implementation and DAO (Data Access Object) classes executing EF Core queries.
- **Naming**: `{Entity}DAO.cs` (e.g., `ClassroomDAO.cs`, `SubmissionDAO.cs`).
- **Migrations**: Stored in `DAL/Migrations/` — auto-generated by `dotnet ef migrations add`, never hand-edit migrations.
- **Rule**: DAO classes interact with `DbContext` directly. No HTTP context or service-level logic.

#### Layer 3 — `Repository/`
- **Contains**: Repository interfaces (`I{Entity}Repository.cs`) and implementations (`{Entity}Repository.cs`).
- **Sub-folders**: Group by domain feature (e.g., `Repository/ClassRepo/`, `Repository/SubmissionRepo/`).
- **Naming rule**: Use `I{Feature}Repository.cs` for interfaces and `{Feature}Repository.cs` for implementations.
- **Rule**: Repositories wrap DAOs. They do NOT contain business rules or direct HTTP context.

#### Layer 4 — `Service/`
- **Contains**: Business logic interfaces (`I{Feature}Service.cs`) and implementations (`{Feature}Service.cs`).
- **Sub-folders**: Group by feature area (e.g., `Service/ClassService/`, `Service/EvaluationService/`).
- **Rule**: All business validation, orchestration, calculations, and authorization decisions belong here. Services call Repositories only (never DAOs directly).

#### Layer 5 — `TeacherPlatform/` (API Project)
- **Contains**: ASP.NET Core API controllers, middleware, filters, `Program.cs`, and configuration files.
- **Controllers**: Located in `TeacherPlatform/Controllers/` with suffix `Controller.cs` (e.g., `ClassController.cs`).
- **Rule**: Controllers handle HTTP requests, model binding, and return HTTP status codes (`Ok`, `BadRequest`, `NotFound`). They inject `I{Feature}Service` only. Never put database or business logic in controllers.

## 4. Frontend Architecture (`FE_Teacher_Platform/src/`)

### Tech Stack
- **Framework**: React 19 (TypeScript)
- **Build Tool**: Vite 8
- **Styling**: Tailwind CSS v4 (`@tailwindcss/vite` + `@import "tailwindcss";` in `src/index.css`)
- **Linter**: Oxlint (`oxlint`)

### Folder Responsibilities

| Folder | Responsibility | Naming Convention |
|---|---|---|
| `components/{feature}/` | Feature-specific reusable UI components | `PascalCase.tsx` |
| `components/ui/` | Primitive UI elements (buttons, inputs, modals, cards) | `PascalCase.tsx` |
| `pages/` | Route/page containers. Compose components & own route state | `kebab-case.tsx` or `{Name}/index.tsx` |
| `services/` | API client classes/functions (all `fetch` / `axios` calls) | `PascalCaseService.ts` or `camelCaseService.ts` |
| `hooks/` | Reusable React hooks for state, queries, side-effects | `use-{kebab-case}.ts` |
| `lib/` | Infrastructure clients (API client instance, auth helper) | `camelCase.ts` |
| `types/` | Shared TypeScript types, interfaces, and enums | `camelCase.ts` or `{feature}.types.ts` |
| `data/` | Static constants, lookup tables, test mocks | `kebab-case.ts` |
| `utils/` | Pure utility functions with no React dependencies | `camelCase.ts` |

### Frontend Cheat Sheet

| What you're adding | Target Path | Naming Example |
|---|---|---|
| New page / route | `FE_Teacher_Platform/src/pages/{name}.tsx` | `pages/class-management.tsx` |
| Feature component | `FE_Teacher_Platform/src/components/{feature}/{Name}.tsx` | `components/class/ClassCard.tsx` |
| UI primitive | `FE_Teacher_Platform/src/components/ui/{Name}.tsx` | `components/ui/Button.tsx` |
| API service | `FE_Teacher_Platform/src/services/{name}Service.ts` | `services/classService.ts` |
| Custom hook | `FE_Teacher_Platform/src/hooks/use-{name}.ts` | `hooks/use-classes.ts` |
| TypeScript definitions | `FE_Teacher_Platform/src/types/{name}.ts` | `types/class.ts` |
| Utility function | `FE_Teacher_Platform/src/utils/{name}.ts` | `utils/formatDate.ts` |

### Frontend Separation Rules & Anti-Patterns
- **Do not put API calls in components or pages**: All HTTP requests belong in `services/`.
- **Do not put JSX inside services, utils, or hooks**: Keep pure logic separated from visual rendering.
- **Do not create `.js` or `.jsx` files**: Strictly use TypeScript (`.ts`, `.tsx`).
- **Keep components focused**: Extract logic into hooks if a component exceeds ~200 lines or mixes concerns.

## 5. Backend API & Security Standards

- **Authentication**: All endpoints (except public authentication/registration routes) MUST require `[Authorize]`.
- **User Identity**: NEVER trust a `teacherId` or `studentId` passed in the request body/query for security-sensitive operations. Extract the verified identity from the JWT claims:
  ```csharp
  var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);
  ```
- **DTOs for All Endpoints**: ALWAYS accept and return DTOs. NEVER expose EF Core database entities directly to API responses to prevent circular references and data leaks.
- **Dependency Injection**: Register all services and repositories in `BE_Teacher_Platform/Teacher_Platform/TeacherPlatform/Program.cs`:
  ```csharp
  builder.Services.AddScoped<IClassRepository, ClassRepository>();
  builder.Services.AddScoped<IClassService, ClassService>();
  ```
